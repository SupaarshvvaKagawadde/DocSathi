# PDF instruction drafts and resumable intake

Instructions are actual uploaded originals. From Checklist, choose **Draft from instructions PDF**, select an inspected PDF, generate proposals and inspect the exact page excerpts. The review screen shows the rendered source page beside each proposal and the exact quoted span below it; choosing a proposal moves the preview to its page. Proposals begin optional. Configure applicability, document combinations and constraints, explain every accepted or rejected proposal, and acknowledge completeness before activation. Manually add missed items. The deterministic extractor is conservative: it matches explicit upload/submit/provide obligations and items listed under headings such as “Documents to be uploaded”, joins lines that wrap mid-sentence while keeping the exact source span, merges repeats across pages (listing the other pages) and names each item from its document phrase. It reads file-size ranges, maximum and minimum sizes, pixel dimensions, page limits and accepted formats from the wording, flags limits above the service maximum and formats the service cannot accept, and suggests conditions for explicit category, disability, scribe, name-change and appearing-candidate clauses. Every suggestion stays editable and inactive until the applicant applies it. It cannot prove completeness or automatically interpret every conditional clause. OCR uncertainty, unreadable pages and truncation remain visible.

Drafts retain the original document ID, SHA-256, page number and exact character span. Confirmation records the account owner, timestamp, decisions and edited requirements. Confirmed drafts survive later drafting; deletion of the original cascades its drafts and invalidates the active source-dependent checklist. Old reports remain historical unless document deletion removes dependent records. This is applicant confirmation, not independent institutional certification.

The browser sends original bytes in chunks up to 512 KiB. Sessions persist for 24 hours in SQLite, including the saved offset and checksum. A folder is created only when the whole original has been received, verified and accepted. A dropped connection, timeout or server restart is retried automatically with backoff (0.5 to 8 seconds); while the browser is offline the upload waits and continues from the last acknowledged chunk when the connection returns, with a visible status line. After a reload or on another device, **Unfinished uploads** lists each saved session with how much has arrived; choosing **Finish upload** and selecting the same file (matched by name, size and checksum) continues from the saved offset, and **Discard** removes it. Selecting the same original in any upload control also finds the saved session. The browser caches only the account-scoped session reference, filename and checksum; file bytes are not stored in browser storage. Repeated finalization returns the saved result without duplicating files or folders. Existing multipart API clients remain supported.

Sessions enforce ownership, CSRF, expiry, inclusive original service limits, ten pending uploads and a 30 MB reservation budget per account. Chunk offsets and final checksums are verified. Each chunk is its own row keyed by session and offset, written with a compare-and-set on the saved offset so concurrent tabs cannot interleave bytes; the session's 24-hour expiry slides forward with each accepted chunk, and finalization assembles the rows in order, verifies size and SHA-256, then removes them. Older single-blob sessions are converted on startup. Partial sessions do not become documents. Account/folder/original erasure cascades session data. Hourly cleanup and startup cleanup remove expired sessions. Session bytes are included in the encrypted metadata backup. Deployment must preserve the private SQLite directory across restarts; a lost server disk cannot be reconstructed from the browser reference.
